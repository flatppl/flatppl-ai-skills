# Changing a FlatPPL grammar

`flatppl-grammars/` holds the syntax grammars in several targets that must stay in
sync: **tree-sitter**, **TextMate**, **Pygments**, **Kate**, **CodeMirror**, plus
`cspell` and the shared `keyword-lists.json`. Many are generated by
`flatppl-grammars/tools/gen-grammars.py`; discover the actual layout live
(`ls flatppl-grammars/`), it grows. Paths are relative to the repo root; if
`cd flatppl-grammars`/`ls` comes back empty (you're in a subdir or worktree), resolve
the root first — don't proceed from memory on an empty listing.

This skill edits/verifies the **grammars**. It does NOT define the language (the
spec is `flatppl-design/docs/05-syntax.md`; read it via `flatppl-docs`), write
`.flatppl` models (use `flatppl-author`), or audit engine semantics (use
`flatppl-conformance-audit` / `flatppl-engine-debug`).

## The one rule: grammars are under-test, not ground truth

The grammars are young (tree-sitter `0.0.1`) and may mis-parse or mis-highlight even
when nothing errors. **"Parses with no ERROR node" is NOT proof of correctness** — a
grammar can silently mis-nest (wrong precedence/associativity) and still report no
error. So:

- Decide correctness against **actual parse trees + the repo's own suite**, never by
  eyeballing the grammar or trusting the README.
- The spec `05-syntax.md` (the formal grammar + supported/excluded constructs) is the
  authority for *what should parse*; the corpus is how you prove the grammar matches.
- Anything built **on** the grammar — editor injection queries, highlight queries,
  tooling keyed on node names like `doc_line` / `call_expression` — inherits this
  uncertainty. Verify it against a real parse tree, not against node names you assume.

## Workflow

1. **Locate the targets and the spec rule.** `ls flatppl-grammars/`; for a
   syntax/keyword change, pull the governing `05-syntax.md` section (and the relevant
   catalogue — `07-functions.md` / `08-distributions.md` for builtins) via
   `flatppl-docs`, and quote it. Keywords/builtins live in `keyword-lists.json`; don't
   hand-edit each target's copy if it's generated — change the source and regenerate.
2. **Make the change.** For tree-sitter, edit the grammar source, then regenerate:
   `cd flatppl-grammars && pixi run gen-tree-sitter` (wraps `npx tree-sitter
   generate`). For generated targets, run `gen-grammars.py` rather than editing
   output by hand.
3. **Add a corpus case for the construct you touched.** tree-sitter test corpus lives
   under `flatppl-grammars/tree-sitter/test/corpus/` — add the input + expected tree
   so the new/fixed parse is pinned. A change with no corpus case is unverified.
4. **Run the suite — don't eyeball.** `cd flatppl-grammars && pixi run check` runs the
   full graph: `check-grammars`, `test-pygments`, `test-kate`, `test-textmate`,
   `check-tree-sitter` (which runs the corpus via `test-tree-sitter` →
   `run-corpus.sh`, then the highlight queries). After any keyword/builtin change also
   run `pixi run check-spec-keywords` — it checks `keyword-lists.json` against the
   spec, catching a grammar that drifted from the catalogue. CI runs the same `check`.
5. **Inspect the tree for the changed construct.** Beyond pass/fail, look at the
   actual parse of your construct (the corpus expected-tree, or
   `npx tree-sitter parse <file>`) and confirm the **nesting/precedence** is what the
   spec implies — this is where a no-ERROR grammar silently lies.

## Report format

State separately what you **verified** (ran `pixi run check`, saw the corpus tree,
parsed the construct) versus what you **assumed** (trusted a query/README). For each
finding cite the spec **section heading** it rests on and the target(s) affected. If a target
is out of sync with `keyword-lists.json` or the spec, flag it rather than assuming the
generator already fixed it.
